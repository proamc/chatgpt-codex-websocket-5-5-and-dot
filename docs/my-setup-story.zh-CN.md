# 我想要的，只是打开 ChatGPT 后能好好用

我曾经以为，Clash 的系统代理开了，软件上网这件事就该交给它了。

但实际用起来，浏览器能打开网页，ChatGPT/Codex 还是会冒出 `request timed out`，接着是“正在重新连接”。dot 有时能和我说话，却连不上我面前这台 Mac。

我也试过打开 TUN。结果在这套环境里，其他应用开始没网，有的网页还跳回登录页面。我想要的其实很简单：保留已经可用的系统代理，让 ChatGPT 和 dot 知道怎么找到 Clash，而不是再把整台电脑的网络翻一遍。

## 我后来分清了两件事

第一件事，是“你有没有走代理”。

系统代理像一张放在大厅里的通知：“需要上网，请找 Clash。”浏览器可能会去看，另一个程序里的网络客户端却未必采用同一套设置。网页能访问，不等于应用里的每一个连接都已经经过代理。

我给 ChatGPT 做了一个很小的启动入口。每次打开时，它把本机 Clash 的地址交给原版应用；原版应用启动的 dot 执行器，也能继承这些代理变量。软件是否使用这些变量，仍取决于它所用的网络库，所以还要看实际连接结果。

第二件事，是“模型请求通过什么方式传输”。

模型请求可以使用 Responses 的 WebSocket 传输，也可以使用 HTTPS。在这次排查里，模型 WebSocket 请求出现过超时；为新聊天关闭该提供商的 WebSocket 支持后，连续 6 次短请求都通过了 HTTPS，未出现模型重试。

这是一次短时测试的结果。它没有证明所有节点、所有网络都适合这样配置，也没有让不稳定的代理节点从此不再超时。

## dot 并没有被我改成“完全不用 WebSocket”

这是我特别想讲清楚的一点。

模型请求和 dot 连接本机，是两条不同的通道。模型可以切换到 HTTPS；dot 的本机执行器仍可能用 WebSocket / WSS 和云端保持连接。

我处理 dot 的办法，是让它正确获得代理。恢复后，我让它在连接的 Mac 上真正查了一次系统版本，拿到了本机执行结果。

所以这套方案的准确说法是：**模型请求改用 HTTPS；dot 仍按自己的协议连接，但通过显式代理改善它的网络路径。**

## 换一台新 Mac，我会这样做

我先安装原版 ChatGPT/Codex 和 Clash Verge，导入自己的订阅，确认一个可用节点。然后保持规则模式、系统代理开启、TUN 关闭，记下自己的 HTTP / Mixed 端口。

接着，我下载这个仓库的启动器，放到个人“应用程序”文件夹，拖进程序坞。第一次打开，填上端口和原版应用路径。以后使用时，先开 Clash，再点这个图标，不再弹终端，也不用盯着一堆启动文字按回车。

如果我还需要解决模型 WebSocket 超时，就按 [配置说明](model-https.zh-CN.md) 单独备份并修改 Codex 的用户配置。保存后我会完整退出、通过新入口重开，再新建一个本地聊天，检查它是否从第一条模型请求开始使用 HTTPS。

最后，我重新授权 dot 访问这台新 Mac，让它做一次只读的系统版本查询。过一会儿再查两次。电脑列表显示在线，只是开始；能真的执行，才是我要的结果。

## 这样做，我少折腾了什么

我不必为了一个应用把 TUN 一直打开，也不必把代理变量写进整个账号的登录环境。启动时不用终端，退出后也不需要清理一堆全局设置。

我把“模型的传输方式”和“dot 的代理路径”分开验证，出问题时终于知道该查哪一段。它不能替我修好每一个节点、每一种 DNS 和路由冲突，但它把我日常需要的路径缩短了：

**打开 Clash，点开 ChatGPT，让 dot 真正连到这台电脑。**

这份经历来自一套 macOS 环境。请在你的电脑上完成 [验收表](new-mac.zh-CN.md#验收表)，再决定是否把它作为自己的日常入口。
