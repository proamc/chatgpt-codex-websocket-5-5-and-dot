# 排错、设置范围与卸载

| 现象 | 检查方向 |
| --- | --- |
| 点开仍出现终端 | 应该打开 `.app`，不是旧的 `.command` 文件或源脚本 |
| 提示代理端口未响应 | Clash 是否运行；填写的是 HTTP / Mixed 端口还是 SOCKS-only 端口；按 Option 重设 |
| 提示应用已在运行 | 保存任务，Command + Q 退出原版，再从专用入口打开；入口不会强退应用 |
| 没有找到原版应用 | Option 启动，填写真实 `.app` 路径，不要填写启动器自身 |
| 网页也不可用 | 优先检查节点、订阅与 Clash 分流，暂不同时调整多个开关 |
| 模型还在重试 | 查新聊天的实际提供商、模型传输和节点；HTTPS 也可能因网络不稳定而超时 |
| 模型能聊，dot 失败 | 查本机授权、执行器是否继承代理、WSS 中继日志和实际节点 |
| 开 TUN 后多个应用断网 | 回到系统代理开、TUN 关；TUN 的路由/DNS 兼容属于另外的排查 |
| Telegram 仍不走代理 | 启动变量只给目标应用及子进程；其他软件按各自设置使用代理 |

## 什么叫“显式代理”

系统代理把地址写进 macOS 的网络设置，程序需要主动遵循。这个入口在启动时把代理地址交给原版应用，子进程可以继承。两者可能覆盖不同网络库。

真正转发流量的仍是 Clash。入口不监听端口，不做 TLS 解密，不接管全机路由，不安装证书，也不清除应用登录信息。

代理变量的实际支持取决于客户端。`NODE_USE_ENV_PROXY=1` 对支持该变量的 Node.js 网络栈有作用，但不代表每种网络库都采用它；不要据此跳过真实连接验证。

## 如何判断 WebSocket 错误

先区别模型通道与本机执行器。超时、连接重置、认证错误分别需要不同证据。

- `timeout`：检查实际代理路径、DNS、规则和节点。
- 已认证连接的 `401/403`：再检查登录、服务限制或握手响应。没有认证的探测请求返回 403 不能单独证明账号故障。
- `1006/ECONNRESET`：记录中断时刻，对照节点切换和连接日志。错误码本身不指明根因。
- 证书错误：检查时间、证书与是否存在 HTTPS 检查；不要关闭证书校验。

## 卸载入口

保存任务并完整退出原版应用。删除 `ChatGPT Clash Launcher.app`，移除程序坞里的这个项目。需要清理端口偏好时，再删除 `~/Library/Application Support/ChatGPT Clash Launcher`。

从原版图标重新打开应用，这次不再由本入口注入变量。Clash 系统代理仍按它自身的开关生效。

如果曾添加模型 HTTPS 配置，还要按 [模型配置说明](model-https.zh-CN.md#撤销) 单独撤销。删除启动器不会修改 `~/.codex/config.toml`。

## 报告问题

请提供 macOS、桌面应用、Clash 版本，填写的端口，哪一项测试失败，以及打码后的简短错误和时间。不要贴完整环境变量、账号文件、订阅、Cookie、令牌或含个人路径的整段日志。
