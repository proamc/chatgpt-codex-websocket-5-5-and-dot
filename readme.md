# Clash + ChatGPT / Codex + dot：我的 Mac 代理配置方法

我希望打开 ChatGPT 后，就能安心把事情交给它：对话能够继续，Codex 能完成请求，dot 也能真正用上眼前这台 Mac。

但在一段时间里，我遇到的情况是：浏览器明明能上网，应用却反复显示 `request timed out`、`正在重新连接`；dot 有时可以聊天，却无法完成本机操作。打开 TUN 后，另外一些软件又出现了断网或登录异常。

后来，我把问题拆开处理，留下了这套配置：**Clash 系统代理开启、TUN 关闭；通过专用图标启动原版应用；为新的 Codex 聊天配置 HTTPS 模型传输。**

这份仓库记录的就是具体做法。它只有两份文档，不需要下载安装包。

| 文件 | 用途 |
| --- | --- |
| [readme.md](readme.md) | 了解原理、操作顺序和验证方法 |
| [forchatgpt.md](forchatgpt.md) | 交给新电脑上的本地助手，检查环境并完成配置 |

## 先讲清楚：我改变了什么

最初让我困惑的是，系统代理已经打开，为什么应用还会连不上？

原因在于，系统代理需要软件主动采用。同一个桌面应用里，不同的网络客户端也可能采用不同的代理机制。浏览器可以访问网页，只能说明浏览器这条路径正常，不能证明 dot 的本机执行器也已经经过 Clash。

因此，我给原版 ChatGPT 做了一个专用启动入口。它在启动时明确传入本机代理地址，应用启动的子进程可以继承这些参数。这样，我就能单独检查 ChatGPT 和 dot 执行器的代理，而不必为了这两个程序持续开启 TUN，或把代理变量写进整个账号的登录环境。

另一个问题来自模型请求的传输方式。在这次排查中，模型 WebSocket 请求出现过超时。我单独为 Codex 提供商关闭了 Responses WebSocket 支持，再用新聊天验证 HTTPS 传输。

这两项修改分别处理不同的连接：

| 连接 | 处理方法 | 需要验证的结果 |
| --- | --- | --- |
| Codex 模型请求 | 配置提供商使用 HTTPS 模型传输 | 新聊天实际使用 `responses_http`，请求能够完整结束 |
| dot 本机执行器 | 通过启动环境传入显式代理 | 执行器获得代理，dot 能在这台 Mac 上完成真实操作 |

**dot 的本机连接仍可能使用 WebSocket / WSS。** 这里没有把整个 ChatGPT 或 dot 改成“完全不用 WebSocket”。模型走 HTTPS，以及 dot 的连接正确经过 Clash，需要分别配置、分别验证。

## 换一台新 Mac，我会按这个顺序恢复

### 第一步：先把 Clash 的基础连接确认好

安装官方的 Clash Verge Rev 和 ChatGPT/Codex 桌面应用，导入自己的订阅，登录自己的账号。先用浏览器访问需要的服务，确认节点可用。

然后保留这套设置：

| 设置 | 使用方式 |
| --- | --- |
| Clash 模式 | 规则模式，核对实际连接命中的规则与节点 |
| 系统代理 | 开启 |
| TUN / 虚拟网卡 | 关闭 |
| HTTP / Mixed 混合端口 | 使用本机实际端口，常见值为 `7897` |
| 允许局域网 | 仅本机使用时可以关闭 |

这一阶段先不同时调整 DNS、路由、Tailscale 或其他 VPN。基础网页连接还没有恢复时，先处理节点和分流，后面的应用配置再继续。

### 第二步：请本地助手制作专用启动入口

在新电脑上打开有本机操作能力的 ChatGPT/Codex，把 [forchatgpt.md](forchatgpt.md) 交给它，并发送：

> 请按这份指南检查并配置这台 Mac。先核对我的 Clash 端口和原版应用路径，再制作不弹终端的专用启动入口、固定到程序坞，并分别验证模型 HTTPS 与 dot 本机连接。

这份指令会让助手根据新电脑的实际环境制作入口。正常使用时，点击图标即可打开原版应用，不应出现终端窗口或“按回车关闭”的提示。

入口准备好以后，先保存正在进行的任务，用 `Command + Q` 完整退出原版应用，再从专用图标打开。已经运行的程序不会因为创建了新图标，就自动获得新的启动参数。

### 第三步：单独配置 Codex 模型 HTTPS

下面的配置针对 Codex 模型通道。编辑前退出应用并备份 `~/.codex/config.toml`，保留自己的模型和其他设置。

把这个键放在第一个 `[表名]` 之前；已有同名键时替换：

```toml
model_provider = "openai_https"
```

在文件末尾添加下表；已有同名表时更新，不重复添加：

```toml
[model_providers.openai_https]
name = "OpenAI HTTPS"
requires_openai_auth = true
wire_api = "responses"
supports_websockets = false
```

这里保持 OpenAI 的既有登录方式，不填写第三方 `base_url`。内置 `openai` 提供商 ID 是保留项，不要用同名表覆盖。

保存后，从专用入口重启应用，**新建一个本地 Codex 聊天**。旧聊天可能保留创建时的提供商，因此需要核对新聊天的实际传输，不能只看配置文件已经写好。

这些操作也已经写入 `forchatgpt.md`。交给本地助手处理时，仍应让它先检查版本兼容性和配置差异。

### 第四步：让 dot 真正在新 Mac 上执行一次

在新 Mac 的 ChatGPT 中打开 dot 资料页，在电脑列表中允许访问这台 Mac，保持电脑联网、应用打开。当前官方说明每个 dot 只能同时连接一台个人电脑，迁移时要确认连接的是新电脑。

我会发送这条只读指令：

> 请在我刚连接的这台 Mac 上查询 macOS 版本和构建号，并查询 uname -s。报告实际工具执行结果。只做只读查询，不读写我的个人文件，不使用云端电脑代替。

电脑显示在线是一个好开始，但拿到这台 Mac 的实际工具结果，才说明本机操作这条路径已经通了。

## 我怎样判断配置已经可用

| 检查项目 | 通过标准 | 我的记录 |
| --- | --- | --- |
| 专用入口 | 点击后能打开原版应用，没有终端窗口 | 未测 |
| 模型对话 | 新本地聊天连续 6 次短请求均完整回复 | 未测 |
| 模型传输 | 对应聊天为 `openai_https`，日志为 `responses_http`，并记录是否重试 | 未测 |
| dot 首次操作 | 实际在这台 Mac 查到系统版本与构建号 | 未测 |
| 约 1 分钟后 | 再完成一次相同的本机查询 | 未测 |
| 约 5 分钟后 | 再查询一次，记录期间断连或重连情况 | 未测 |
| Mac 重启后 | 等 Clash 启动，再点专用入口，重新验证模型与本机操作 | 未测 |

网页能访问、代理端口在监听、电脑显示在线，分别证明不同的环节。把这些结果分开记录，出问题时也更容易找到具体位置。

## 这套做法帮我解决了什么

我保留了原本能工作的系统代理，不再依赖 TUN 才能尝试恢复 ChatGPT 和 dot。模型请求与本机执行器也有了各自的检查方式，排查时不必反复混用同一个“WebSocket 问题”来解释所有错误。

日常操作变得简单了：**先开 Clash，再点程序坞的专用图标。** 不用每次打开终端，也不需要把代理变量扩展到其他新启动的软件。

在原先的测试环境中，新的 Codex 聊天连续 6 次短请求都通过 HTTP 模型传输完成，未见这 6 次模型请求重试；dot 随后也完成了真实的本机系统查询。这些结果说明当时的关键功能已恢复，不能替代新电脑上的验收或长期稳定性观察。

这仍然不是 VPN/TUN 接管方案。Telegram 等其他独立软件需要按自己的支持情况使用系统代理或内部代理。节点、DNS 或出口不稳定时，HTTPS 也可能超时。

## 再遇到问题时，先查哪一段

| 现象 | 优先检查 |
| --- | --- |
| 网页也打不开 | Clash 节点、订阅与分流 |
| 入口提示应用正在运行 | 保存任务，完整退出，再从专用入口打开 |
| 模型仍然重连 | 是否新聊天、实际提供商、传输方式和节点 |
| 模型能聊，dot 本机操作失败 | 本机授权、执行器代理继承、WSS 中继连接与实际出口 |
| 开 TUN 后其他软件断网 | 先恢复系统代理开、TUN 关，再另行排查路由和 DNS |

需要撤销时，先退出应用，再从原版图标打开，便不再由专用入口注入变量；专用入口和程序坞项目可以移除。模型 HTTPS 是独立设置，需要另外还原本次配置字段，保留之后新增的其他设置。
